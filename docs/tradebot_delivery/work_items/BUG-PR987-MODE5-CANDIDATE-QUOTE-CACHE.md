# BUG-PR987-MODE5-CANDIDATE-QUOTE-CACHE

## Classification and outcome

- Type: BUG
- Product area: PR #987 Sentinel Mode 5 completed-bar candidate to option-depth authorization.
- Goal: Preserve an otherwise-valid completed five-minute Mode 5 candidate while option-depth events are lagging, prevent stale/future/out-of-order/superseded/duplicate quotes from authorizing it, and explain candidate-specific quote suppressions in the existing advisor JSONL trace.
- State: Approved for the bounded implementation below; this work item does not issue a live-readiness verdict.

## Current and expected behavior

Current cache age is derived by subtracting the candidate's last in-bar spot timestamp from an option-depth exchange timestamp. A quote that predates that in-bar timestamp can evict the candidate even though evaluation occurred only after the five-minute boundary. Missing option timestamps can fall back to wall time; option events lack per-token source-order protection; final entry authorization can observe a candidate that was superseded after the cache read. Candidate-specific quote suppression is not reliably observable in the advisor trace.

Expected behavior: retain candidate source timestamp as provenance, but define the source-time eligibility boundary as `(completed_bucket_epoch + 1) * 300000` milliseconds. Start the existing 300-second inclusive lifetime at candidate issuance using same-process monotonic time. Require a valid current-session option event timestamp at/after the boundary and a strictly later same-process ingress timestamp within configured `MAX_QUOTE_AGE_SEC` and `MAX_CLOCK_SKEW_SEC` policies. Invalid or lagging quotes cannot authorize or evict a still-valid candidate. Per-token duplicate/decreasing `(exchange_timestamp_ms, sequence_id)` events cannot mutate advisor state. Final reservation is serialized against candidate generation changes; each candidate authorizes at most one reservation attempt. Rollover, expiry, supersession, invalidation, and consumption clear paired state safely.

For an active candidate, emit one trace record for each exact suppression reason: `MODE5_QUOTE_BEFORE_BAR_BOUNDARY` and `MODE5_QUOTE_INGRESS_BEFORE_CANDIDATE_ISSUE`. Deduplicate on `(session, index, candidate_generation, reason)` across all instruments for that candidate. The first quote triggering a reason supplies the representative canonical instrument and quote timestamps in the trace; these fields do not enumerate every affected instrument or quote. The advisor state lock is acquired before a dedicated trace-state lock. Lifecycle transitions update the active generation and clear emitted, attempt, in-flight, and dropped state while both are held briefly. Emission acquires both in that order, confirms the active candidate, and atomically reserves a dedup key, in-flight marker, attempt, immutable record, and monotonically increasing `trace_sequence`. A concurrent same-key event coalesces while a reservation is in flight. Producers serialize the record under the state locks, then use bounded `put_nowait`; they do no filesystem I/O or synchronous logging. The queue defaults to 1,536 items, and each serialized record is limited to 16,384 bytes: at most 24 MiB of queued serialized payload plus one writer-active record, before Python object overhead. These are provisional engineering bounds, not empirically validated market-rate or memory sizing. Queue-full, oversized, unavailable-writer, and serialization failures are decision-neutral and visibly increment health state; drops are sticky per dedup key for the active candidate generation. A daemon worker is the only trace appender and serializes JSONL writes. Successful keyed records deduplicate generic Mode 5 decision traces as well as quote suppressions; each reason/key has at most two actual append attempts, and after two failures the key is sticky-dropped. Attempt caps are candidate-generation scoped and cleared on replacement, expiry, consumption, or session reset. A reserved immutable old-generation record may finish after replacement; its `trace_sequence` preserves reservation order, and completion cannot mutate or repopulate current-generation state. Append order may differ from reservation order. Trace failures, queue saturation, and circuit-open drops must not change quote eligibility, candidate state, reservation, or entry decisions. No further write or producer-side log is generated for a sticky-dropped key. Do not emit suppression records without an active associated candidate.

Each advisor instance has a UUID `trace_run_id`; every queued JSONL record carries that ID and a monotonically increasing per-instance `trace_sequence`. Record identity and within-run order use `(trace_run_id, trace_sequence)`. There is no global sequence across advisors writing to the same append-only path, so file append order alone cannot establish cross-run decision order.

Each emitted suppression JSONL record includes: `event_type=MODE5_QUOTE_SUPPRESSED`, `action=ABSTAIN`, `decision=RETAIN_CANDIDATE`, index, representative canonical instrument, candidate generation, candidate action/setup/bar_time, boundary timestamp, issued monotonic ns, representative quote exchange timestamp, ingress monotonic ns, validated decision timestamp, `trace_run_id`, and `trace_sequence` assigned at reservation. Queued generic Mode 5 records retain their event/reason/details and generation snapshot and include the same run/sequence identity.

Missing/invalid/stale/future/late quotes fail closed without substituting wall time and without evicting a live candidate.
- Per canonical option token, reject duplicate/decreasing `(exchange_timestamp_ms, sequence_id)` before observer/cache/OR/APM mutation; rollover clears watermarks and candidate metadata. A prior-session event cannot affect a new-session candidate.
- Candidate identity/generation, issue time, and status update atomically. Final reservation revalidates the same generation under serialization; compare-and-clear cannot remove a newer candidate. Transient retries are limited to explicit pre-reservation gates with no side effect. Same-key in-flight events coalesce; failed append permits a retry up to the two-attempt reason cap. Successful append alone marks emitted. Trace errors have no decision effect; after the cap there are no more writes or failure logs.
- A reserved immutable record may append after candidate replacement. Its generation and sequence remain historical; its completion cannot alter current candidate state. Append serialization can produce a different file order than reservation sequence, so consumers use `trace_sequence` to reconstruct reservation order.
- Mode 5 decision records produced by `_on_5m_bar_close_locked` and the dispatch-key, reservation-outcome, and final-OR-veto branches in `_evaluate_option_depth` are snapshotted under the advisor lock with candidate generation, immutable details, reason, and trace sequence. Every Mode 5 record is queued nonblocking; the worker alone appends. `_on_5m_bar_close`, `on_tick`, `reconcile_5m_bars`, and `_evaluate_option_depth` preserve snapshot generation/sequence and do not synchronously flush file writes before or after dispatch. Accepted reservations consume the candidate under state lock, then `on_apm_entry` runs with no advisor lock. Queue saturation/drop cannot change callback invocation or candidate one-shot semantics.
- The constructor accepts `mode5_trace_queue_capacity` and `mode5_trace_max_record_bytes` parameters (default 1,536 and 16,384). These are constructor settings, not environment/config migrations. `get_mode5_trace_health()` / `get_mode5_trace_health_snapshot()` expose capacity, depth, enqueue/append counts, queue-full/oversize/unavailable drops, pending-unpersisted count, writer status, last processed sequence, last persisted sequence/error, and degraded state. `last_processed_sequence` advances after each worker item resolves, including terminal failures; `last_persisted_sequence` advances only after a successful append. `shutdown_mode5_trace_writer(timeout_sec)` stops accepting and boundedly drains, returns the full health snapshot including remaining unpersisted records, and logs that snapshot; an atexit hook applies a short bounded timeout. Operations must inspect the health snapshot/shutdown report and require zero drops and zero pending records before treating trace capture as complete. A queue implementation alone does not prove market-rate capacity or readiness.
- The daily capture owner polls the advisor getter only on the monotonic `MODE5_TRACE_HEALTH_INTERVAL_SEC` cadence (default 60 seconds, valid 5 through 3,600; malformed/out-of-range values fall back to default with one sanitized warning). Degraded state logs on transition and at a five-minute heartbeat. Getter/logging failures are isolated from dispatch and their count and last exception type are included in the shutdown report.
- Shutdown ordering is fixed: call streamer disconnect in a daemon worker with a 10-second bound while callback admission remains open; after return, exception, or timeout, close admission; wait up to 10 seconds for admitted callbacks. If callbacks remain active, unregister the exact advisor atexit callback, write a degraded report, and skip recorder shutdown, advisor drain, and stitching. If callbacks quiesce, attempt recorder stop and advisor writer drain in separate bounded daemon workers. Stitch only if recorder flush returned, its worker was observed dead, and its queue was observed empty; otherwise report `SKIPPED_RECORDER_NOT_POSITIVELY_STOPPED`. Never force-kill a timed-out worker. The report records shutdown worker-alive observations; thread-start failures, raised calls, and timeouts have distinct statuses. Late-reject count is a timestamped point-in-time field (`late_callback_rejects_at_report`), not a final total. A disconnect timeout means callbacks may still arrive and be rejected/countable after this snapshot. An active-callback timeout is `CALLBACK_QUIESCENCE_TIMEOUT`, exits nonzero, and records active/late counts, atexit-unregister result, and skipped-stage statuses.
- Health schema validation is strict: missing counters, invalid counters/sequences, or missing/unknown `trace_run_id` produce `status=ERROR`; absent values are never coerced to zero. `append_successes` may not exceed `enqueued`; no equation is imposed between append failures and enqueued/pending because failures count individual attempts and may include retries. `HEALTHY` requires positive capacity and record-size limit, zero queue depth/pending/active writes/drops/failures, writer status `STOPPED`, `append_successes == enqueued`, consistent persisted/processed high-water sequences (both empty/None-or-zero for an empty run), completed disconnect, quiescent callbacks, a stopped recorder with observed dead worker and empty queue, successful report writes and stitch, and no loop error. Recovered append failures remain degraded. Missing proof or any failed/timed-out stage yields degraded run status and nonzero exit. `KeyboardInterrupt` and `SystemExit` are re-raised after bounded cleanup; ordinary loop exceptions run cleanup, are recorded by type, and exit nonzero.
- The main capture owner tracks each successfully initialized recorder, advisor, and streamer from setup onward. A setup exception triggers bounded best-effort cleanup of resources already created, records missing resources as `NOT_CREATED`/unknown, and skips stitch for that partial setup. No partial setup can claim writer or recorder completion without positive health evidence.
- The report distinguishes `trace_capture_status` from `stitch_status`; stitch completion never implies trace completeness. It includes `trace_run_id`, queue/capacity/pending/drop/failure/writer fields, callback active count and timestamped late-reject snapshot, health reporter failures, recorder/disconnect/drain statuses and worker-alive observations, atexit-unregister result, report-write status, and stitch result. The pre-stitch file is retained if stitching fails. A report-write failure does not prevent stitching when callbacks quiesced and the recorder is positively stopped, while callback-timeout and unsafe-recorder policies skip stitching.
- Recorder shutdown is `STOPPED` only when a worker thread was observed and confirmed not alive after `flush_and_stop`; absent worker evidence is `UNKNOWN`, and an absent/nonempty queue prevents `run_capture_status=HEALTHY`.
- Queue publication follows lock order advisor state -> trace state -> health. The producer increments `pending_unpersisted` under the health lock before `put_nowait`, holds the health lock across the nonblocking publication and success-only `enqueued` increment, and rolls pending back while incrementing `queue_full_drops` if the queue is full. A worker may dequeue immediately but cannot complete its health update before publication accounting commits; a health snapshot during that brief commit waits, then sees a consistent state. Tests also verify the reserved pending count before publication and prove a full queue leaves no phantom pending reservation.
- Explicit writer shutdown is serialized and idempotent. Once the worker has stopped, it unregisters the instance's atexit callback even if the final health report remains degraded due to unpersisted records; if bounded shutdown times out with a live worker, the callback remains registered as a process-exit fallback. Test fixtures redirect implicit trace paths to temporary files and boundedly close every writer they create, asserting no worker or retained atexit callback remains.
- A stalled append can occupy the sole worker and fill the bounded queue; later unique records are dropped and health becomes degraded, without blocking the quote callback or vetoing trading decisions. A process interruption or partial write can leave malformed JSONL; no repair or transactional file replacement is added. Serialization and brief lock contention remain on the producer path.
- A trace append that returns failure or raises an ordinary exception counts as a failed attempt. The worker retries at most once, then clears only the matching in-flight reservation, marks the active key dropped, retains `pending_unpersisted` because the record was not persisted, and continues processing later queue items. A stale completion after candidate replacement cannot recreate old-generation state.
- Mode 5 opening-range veto records now use the same `(session,index,generation,reason)` dedup key: successful persistence emits at most one representative record per key; failures retry at most once and then sticky-drop. This bounds repeated-quote trace volume. Dropped-key and health counters remain visible through the health snapshot.

## Rollout and limitations

### Capture shutdown fence and recorder completeness amendment

The capture shutdown path closes a distinct dispatch fence before starting streamer disconnect, while callback admission remains open until disconnect returns, raises, or times out. Every synchronous broadcaster depth/tick call holds a lease; the tick's price-state update is covered by that same lease. A callback denied by the closed fence performs no broadcaster dispatch or corresponding price update. Finalization waits boundedly for both admitted callbacks and active dispatch leases. If either remains active, it reports counts and `order_action_may_be_in_flight` conservatively, skips recorder stop/advisor drain/stitch, and makes no cancellation claim.

Stitching requires `disconnect_status=RETURNED`. A raised, timed-out, or otherwise unconfirmed disconnect yields `SKIPPED_DISCONNECT_UNCONFIRMED` even when recorder and advisor shutdown otherwise look clean. The recorder accounting sink counts each depth input and recognizes `PERSISTENCE_QUEUE_DROPPED_BURST` and `PERSISTENCE_QUEUE_EXHAUSTED`; malformed/unrecognized telemetry or an input error without a matching known-drop event makes accounting unknown. At the stitch boundary, `accounting_known` must be the boolean `true`, `input_error_count` and `unknown_telemetry_count` must both be exactly zero, known drops must be zero, `total_records_written` must exactly match the sum of frozen manifest row counts, and `input_count` must equal `total_records_written + known_drops`. A positively stopped recorder with an empty queue and zero dispatch denials is also required. Any mismatch or uncertain disposition retains source chunks and the report while skipping stitch. These checks do not change strategy, dispatch routing, or broker behavior.

Focused offline acceptance coverage includes callback paused before lease then denied after closure, an active lease timeout skipping all dependent shutdown, depth/tick lease use and tick-state atomicity, successful recorder accounting, both known drop event types, malformed/unknown telemetry, input exceptions, accounting mismatch/drop preventing stitch, disconnect-timeout-only stitch suppression, and a clean positive-accounting run allowing stitch. A pre-existing timezone portability concern is outside this amendment and remains unmodified.

### Frozen stitch manifest amendment

The post-market stitcher consumes only an explicit immutable snapshot of `recorder.written_files` taken after recorder shutdown; it does not discover chunks with globbing. Before reading or writing outputs it validates each entry is unique, a regular `.parquet` file, contained within the expected `chunks` directory, and present. A structurally invalid manifest returns `INVALID_MANIFEST`; a missing or unreadable listed chunk returns `FAILED_CHUNK_READ`. Validation/read failure occurs before writing the stitched master or success summary, preserving any prior files. The finalizer reports every non-`COMPLETED` stitch status as degraded with a nonzero exit. No chunk allocation or recorder behavior changes are included.

Acceptance tests cover mixed readable/unreadable manifest entries and missing, duplicate, and out-of-directory entries, verify prior master/summary files remain byte-for-byte unchanged, confirm an empty frozen manifest does not glob orphan chunks, and verify finalizer propagation of `FAILED_CHUNK_READ` as degraded/nonzero.

### Restart-safe chunk allocation and transactional stitch amendment

`UpstoxAsyncParquetRecorder` accepts a strict nonnegative integer `initial_chunk_index` (default `0`; booleans and coercible strings/floats are rejected before directory or worker creation). After the existing single-instance lock, capture scans only the direct entries of that session's `chunks/` directory, parses `level5_chunk_<digits>.parquet` numerically, rejects malformed matching prefixes, symlinks/nonregular entries, and duplicate numeric indices, then passes the maximum existing index to the recorder. Gaps are preserved and the next allocation is `max + 1`. Existing chunk bytes are never overwritten. Each new chunk is written to a unique same-directory temporary file, fsynced, atomically published with no-replace hard-link semantics, and only then added to `written_files`; a collision or write failure fails closed and does not manifest the incomplete chunk.

After confirmed recorder shutdown, capture freezes the ordered `written_files` tuple and writes a durable, run-correlated source manifest with chunk relative paths, row counts, byte sizes, SHA-256 values, recorder input/write/drop status, date/run IDs, and the count of prior chunks excluded from this run. Coverage is explicitly `CURRENT_RUN_ONLY` and `claims_whole_session_complete=false`; prior chunks are preserved but excluded, including any without a valid prior manifest. `UNKNOWN` or malformed run IDs and manifest, path, accounting, hash, or persistence mismatches prevent stitching.

The stitcher validates and reads only the frozen source-manifest entries, stages a run-specific master and summary under a fresh generation directory, fsyncs both files and their immediate generation directory, and fsyncs each newly created generation-directory parent before atomically replacing `latest_stitch_manifest.json` last. A generation-parent fsync failure occurs before pointer replacement, preserves the previous pointer and aliases, and fails stitching. If pointer replacement itself fails, the old pointer remains current. If pointer replacement succeeds but the following `data_dir` fsync fails, the new pointer may already be visible; report `COMMIT_DURABILITY_UNKNOWN` with its path, run ID, and `VISIBLE_DURABILITY_UNCONFIRMED`, do not refresh aliases, and degrade with nonzero exit. This uncertainty must not be reported as `COMPLETED` or as preserving the old pointer. On confirmed pointer durability, the pointer is authoritative for locating a same-run, hash-verified pair. Existing date-level master/summary paths are refreshed afterward as non-authoritative compatibility aliases. Any failure before pointer replacement leaves the previous pointer and aliases intact; staged orphan files are not current. Alias update failure returns `ALIAS_UPDATE_FAILED`, preserves the committed pointer, and degrades the run. Existing downstream readers are unchanged; they must use `latest_stitch_manifest.json` when they need to verify that master and summary belong to the same run. Historical 1-minute index-candle fetching remains supplemental and outside the stitched-pair transaction.

## GATE-15 durable opening-range retry ledger

The opening-range reconciler persists its retry budget in the versioned India-session ledger at the absolute repository-root path `runtime/sentinel_or_reconciliation_state.json`, derived from the advisor module location and independent of the process working directory. Every ledger must contain exactly `NIFTY`, `BANKNIFTY`, and `SENSEX`, each initialized with an attempt count and timestamp; missing or extra indices invalidate the whole ledger. Each index has an independent maximum of 10 attempts. The attempt count and timestamp are atomically reserved and durably synced before the historical-candle request; `force=True` may bypass the 60-second throttle but never the cap. The persistent sidecar lock (`.json.lock`) and `flock` serialize processes. Network calls occur after the lock is released.

First bootstrap is allowed only when the ledger, sidecar lock, and independent sibling marker (`.sentinel_or_reconciliation_state.initialized`) are all absent. Bootstrap durably creates and locks the sidecar, exclusively writes and fsyncs an `INITIALIZING` marker with absolute path identity, atomically creates/fsyncs the initial ledger with all three indices, then atomically replaces and fsyncs the marker as `READY`. It returns bootstrap success only after the READY file and parent directory are synced. Normal loads require a valid READY marker, ledger, and lock. Any partial combination, INITIALIZING marker on restart, malformed marker, or identity mismatch fails closed; it never recreates a missing sidecar. If READY replacement is visible but its fsync reports uncertainty, the current process still issues no request; a restart may proceed only after validating READY plus the ledger and lock, and must durably reserve the attempt before requesting candles. The ledger also fails closed on malformed state, lock/read/write/permission/fsync errors, clock regression, or stale-session events. Degraded paths emit sanitized errors and make no candle request. A verified newer India session resets prior retry state; an older event cannot move it backward.

A successful exact 30-candle proof stores the normalized 09:15–09:44 IST bars, source and coverage metadata, and SHA-256 digest. On restart, the exact parser and digest are checked again before bounds or `COMPLETE` state are restored. A bare `COMPLETE` marker is invalid. Tests inject a ledger under `tmp_path`; they never create or modify the production runtime ledger.

No new configuration key is introduced. Existing installations with the earlier ledger and lock but no initialization marker will abstain after this change until separately authorized, audited recovery validates the state and establishes the marker. Preserve the ledger, `.json.lock` sidecar, and `.initialized` marker together across advisor restarts. Do not delete the marker to reset retry state. If any subset is missing, reconciliation abstains; stop all advisors and use separately authorized, audited recovery. Total loss of all three artifacts is the explicit state-loss limit: it is indistinguishable from genuine first use and will pass the all-absent bootstrap check. Operators must preserve all three and treat any suspected total loss as requiring separate authorization before restarting; this code cannot detect or reconstruct erased state. This implementation does not change opening-range eligibility, strategy thresholds, broker routing, or order behavior, and does not establish live readiness.

Focused offline validation covers incomplete index ledgers at zero and after NIFTY/BANKNIFTY reach the cap; clean first-use bootstrap; partial/malformed bootstrap states; cap-state loss with the marker preserved; working-directory independence without production runtime access; a two-process final-slot race using independent processes and the shared sidecar lock; and injected failure at lock creation, all marker/ledger writes, each file and directory fsync, temporary-file creation, and both atomic replacements. Every injected failing process makes zero API requests. Restart from INITIALIZING or partial artifacts abstains; restart from a visible READY marker after fsync uncertainty validates state and makes only durably reserved requests.
