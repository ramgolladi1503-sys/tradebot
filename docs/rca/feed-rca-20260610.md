## 3. Root Causes (10 Identified)

---

### RC-1 · ReactorNotRestartable → Permanent FEED_LIFECYCLE_FATAL

**Severity:** CRITICAL — Single event kills the entire session.

**What happens:**  
On the first WS 1006, `restart_depth_ws` calls `stop_depth_ws` then immediately calls `start_depth_ws` inside the same Python process. `start_depth_ws` (line 6165) calls:

```python
from twisted.internet import reactor
if getattr(reactor, "_started", False) and not getattr(reactor, "running", False):
    raise RuntimeError("ReactorNotRestartable: Twisted reactor was started and stopped")
kws.connect(threaded=True)
```

After the first `stop_depth_ws`, the Twisted reactor has been started and stopped. Every subsequent `start_depth_ws` call raises `ReactorNotRestartable`. This is caught at line 6171–6173, which calls `_set_reconnect_blocked_reason("reactor_not_restartable_…")`. That sets:

- `_RECONNECT_BLOCKED_REASON = "reactor_not_restartable_…"`
- `_RUNTIME_STATE = "FEED_LIFECYCLE_FATAL"`
- `_REACTOR_NOT_RESTARTABLE_DETECTED = True`

**The watchdog (line 5780–5786) then immediately exits its `while True` loop** when `_reconnect_recovery_blocked_active()` returns True. The feed is permanently dead for the session.

**Root cause:** Kite KiteTicker uses Twisted internally. The Twisted reactor is a process-singleton that cannot be restarted in the same process. Once the first full stop-and-restart cycle occurs, every subsequent `kws.connect(threaded=True)` call raises `ReactorNotRestartable`.

**Evidence:** Lines 6164–6200 (`start_depth_ws`), lines 5780–5796 (watchdog breaks).

### RC-2 · WS 1006 Recovery Path Escalates to TERMINAL Too Quickly

**Severity:** HIGH

`_handle_ws1006_recoverable` (lines 1372–1469) classifies "connection was closed uncleanly" as `RECOVERABLE_WS_DROP`. The coordinator budget is:

```python
DEPTH_WS_WS1006_RECOVERABLE_MAX_ATTEMPTS_PER_SESSION = 2  # default (line 1285)
```

With 13 WS 1006 events in a session, the coordinator exhausts its 2-attempt budget almost immediately. After the 2nd attempt, `decision.action = "TERMINAL"` → `_block_reconnect_for_process_restart` → `FEED_LIFECYCLE_FATAL`.

**The soft-resubscribe path (lines 1439–1468)** requires `_ws_connected_state() is True` AND `_LAST_WS_TICK_EPOCH` fresh within 2 seconds. After a 1006 disconnect, `ws_connected=False`, so soft resubscribe always returns `False`. Code logs `FEED_WS_1006_RECOVERY_SOFT_RECONNECT_FAILED` and falls through to DEGRADED with no recovery.

### RC-4 · Watchdog Exits Permanently on recovery_blocked

**Severity:** CRITICAL

The watchdog loop (lines 5777–6141) has TWO break points:

```python
# Line 5780-5786 (before sleep)
if _reconnect_recovery_blocked_active():
    _emit_reconnect_recovery_blocked_snapshot(...)

# Line 5790-5796 (after sleep)

```

Once `_RECONNECT_BLOCKED_REASON` is set, **the watchdog thread dies**. The thread is non-daemon (`watchdog_thread.daemon = False`, line 6154), so the Python process lives on, but no monitoring, no option subscription retries, no snapshot emissions.

### RC-5 · Phase2 Hard-Gated on `feed_ok` — Zero Candidates When Feed Unverified

**Severity:** HIGH

`build_candidates_phase2` (engine_phase2_adapter.py, lines 367–415):

```python
feed_ok = bool(feed_payload.get("feed_ok"))
if not feed_ok:
    out = []  # ALL CANDIDATES DROPPED
```

`feed_ok=True` requires simultaneously:
1. `ws_connected=True`
2. `last_tick_age_sec ≤ 2.5s`
3. `last_depth_age_sec ≤ 6.0s`
4. `option_feed_verification.state == "OK"`
5. `feed_truth_state != "DEAD"`

During startup warmup, after any WS reconnect, and whenever option ticks are unverified, `feed_ok=False`. Phase2 returns zero candidates even when the underlying data is arriving normally.

### RC-6 · Option Tick Verification State Not Reset on Soft Resubscribe

**Severity:** HIGH

`_reset_option_feed_verification` is called in:
- `stop_depth_ws` ✓
- `on_connect` ✓

But **NOT** in `_soft_resubscribe_current` or `_resubscribe_full` (except when called from `on_connect`). If soft resubscribe succeeds but the verification state is stuck in `FAILED` from a previous cycle, `feed_ok` stays False.

**Root cause:** Option verification is coupled to the hard TCP connect lifecycle, not the subscription replay lifecycle.

---

### RC-7 · Soft Resubscribe Is Not a Recovery Mechanism (Misleadingly Named)

**Severity:** MEDIUM-HIGH

`_soft_resubscribe_eligibility` (lines 932–953) requires `_ws_connected_state() is True`. After any WS 1006 disconnect, `ws_connected=False`, so eligibility returns `(False, "ws_disconnected")` immediately.

Soft resubscribe can only be used to refresh tokens on an already-healthy connection. It cannot recover from a 1006. The name suggests recovery capability, but the gate prevents it.

Result: after every 1006, soft resubscribe silently fails, and the code falls through to `_schedule_restart_depth_ws` which triggers RC-1.

---

### RC-8 · FEED_RESTART_STORM_TRIP == FEED_MAX_FULL_RESTARTS_PER_HOUR (Config Design Flaw)

**Severity:** HIGH (same as RC-3, different angle)

The storm breaker is meant to detect an abnormal **burst** of restarts. With both values at 6, it trips at the hourly rate limit — meaning any normal session that needs 6 restarts (about 1 per hour) permanently loses restart capability for the rest of the session.

For a 6-hour Indian market session with 13 WS 1006 events observed, 6 allowed restarts is inadequate.

---

### RC-9 · No Process-Level Supervisor — FEED_LIFECYCLE_FATAL Is Permanent

**Severity:** HIGH — systemic

The orchestrator main loop (lines 4819–4831) sees `FEED_LIFECYCLE_FATAL` and:

```python
if is_fatal:
    logger.warning("orchestrator_live_monitoring_feed_fatal_sleep state=%s", rstate)
    time.sleep(max(2.0, self.poll_interval))
    continue
```

It sleeps and loops forever. It does not attempt a process restart, does not call any recovery function, does not exit with a non-zero code that a supervisor could catch.

No supervisor script (`supervisord`, `systemd`, or shell loop) is wired to the live run. `run_live.sh` starts the process once without a restart loop.

**Contract broken:** The codebase assumes an external supervisor will restart the process on `FEED_LIFECYCLE_FATAL`. That supervisor does not exist.

### RC-10 · Option Verification Timeout Too Short at Market Open

**Severity:** MEDIUM

Default: `FEED_OPTION_VERIFY_TIMEOUT_SEC = 15.0` (line 2047).

At 9:15–9:30 IST market open:
1. Kite delivers option ticks with 5-20s latency
2. WS connect + subscribe + first tick can take 10-25s
3. The 15s verification window expires before ticks arrive

When verification times out, `state = "FAILED"` (not transient — permanently FAILED until hard restart). This blocks `feed_ok` indefinitely, starving Phase2 of candidates for the entire market session unless a full WS restart clears it.

## 5. Modification Suggestions

> **Hard rules maintained:** No live execution changes. No order placement. No risk gate weakening. All modifications proposable in a narrow-scope PR with tests.

### MOD-1 · Run KiteTicker in a Dedicated Subprocess (Fixes RC-1, RC-4, RC-9)

**Problem solved:** ReactorNotRestartable is impossible when each KiteTicker instance runs in its own subprocess. The Twisted reactor starts fresh per process.

**Proposed design:**

Create `core/kite_ws_subprocess.py`:
- Spawns `kite_depth_ws` feed in a **child process** using `multiprocessing.Process`.
- Child process runs the full WS lifecycle (connect, subscribe, on_ticks, watchdog).
- Parent process monitors child via a shared health file (`runtime/ws_subprocess_health.json`) written by the child every N seconds.
- On FEED_LIFECYCLE_FATAL or child process death, parent kills the child and spawns a fresh one.
- **No shared in-process state** between parent and child (all via SQLite + JSON files, already the existing contract).

**Key safety contracts maintained:**
- Child writes tick data to SQLite DB (existing path, existing schema).
- Child writes `feed_runtime_latest.json` (existing path).
- Parent only reads both; never writes tick data.
- `broker_api_called=false` in child (WS subscribe only, no orders).
- `allowed_for_live_execution=false` in child process.

**Scope:** New file `core/kite_ws_subprocess.py` + orchestrator method `_start_feed_subprocess`. No changes to `kite_depth_ws.py` required initially.

### MOD-7 · Option Verification: Add SOFT_FAIL State (Fixes RC-5, RC-10)

**Problem:** Verification timeout permanently blocks `feed_ok`. This is too strict.

**Proposed:** Add `SOFT_FAIL` state:
- `SOFT_FAIL`: timeout occurred but ≥1 tick received per required symbol. Feed is degraded but usable.
- `FAILED`: timeout occurred AND zero ticks for ≥1 required symbol. Feed is blocked.

**In `derive_feed_ok()`:**

```python
option_verify_state = str((option_feed_verification or {}).get("state") or "").upper()
# SOFT_FAIL: allow feed_ok=True but emit feed_degraded=True
option_ok = option_verify_state in {"OK", "SOFT_FAIL"}
```

**Sa-fety:** `feed_ok` still goes False on hard verification failure (zero ticks). Phase2 candidates tagged with `feed_degraded=True` carry evidence of soft-fail state. No execution gate is removed; Phase2's hard blockers still apply.

### MOD-8 · Watchdog Must Not Exit on recovery_blocked — Enter Monitoring Mode (Fixes RC-4)

**Replace `break` in watchdog `_watchdog` (lines 5780–5796) with a monitoring sub-loop:**

```python
if _reconnect_recovery_blocked_active():
    blocked_reason = str(_RECONNECT_BLOCKED_REASON or "").strip().lower() or "unknown_reconnect_block"
    _emit_reconnect_recovery_blocked_snapshot(source="watchdog:recovery_blocked", reason=blocked_reason)
    # Enter monitoring mode instead of dying
    while not (_WATCHDOG_STOP is None or _WATCHDOG_STOP.is_set()):
        time.sleep(5.0)
        _emit_reconnect_recovery_blocked_snapshot(source="watchdog:monitoring_fatal", reason=blocked_reason)
        # If subprocess restart (MOD-1) cleared blocked state, resume outer loop
        if not _reconnect_recovery_blocked_active():
            break
    break  # Only break outer loop when watchdog stop is set
```

**Safety:** Watchdog only reads state and emits logs. No order actions. No risk changes.

### MOD-10 · Add Process-Restart Shell Supervisor (Fixes RC-9)

**New file:** `scripts/run_live_supervised.sh`

```bash
#!/usr/bin/env bash
# Safe live run supervisor — wraps main.py with restart on fatal exit.
# Does NOT enable live orders. Does NOT change safety gates.
# ALLOW_LIVE_ORDERS, MANUAL_APPROVAL_REQUIRED etc. must be set by caller.

set -euo pipefail
MAX_RESTARTS=${LIVE_SUPERVISED_MAX_RESTARTS:-10}
RESTART_WAIT_SEC=${LIVE_SUPERVISED_RESTART_WAIT_SEC:-15}
RESTART_COUNT=0

echo "[supervisor] Starting tradebot supervised run. MAX_RESTARTS=$MAX_RESTARTS"

while [ $RESTART_COUNT -lt $MAX_RESTARTS ]; do
    ATTEMPT=$((RESTART_COUNT+1))
    echo "[supervisor] Attempt $ATTEMPT/$MAX_RESTARTS"
    python main.py "$@" || EXIT_CODE=$?
    EXIT_CODE=${EXIT_CODE:-0}
    RESTART_COUNT=$((RESTART_COUNT+1))
    if [ $EXIT_CODE -eq 0 ]; then
        echo "[supervisor] Clean exit (code 0). Not restarting."
        break
    fi
    echo "[supervisor] Exited code=$EXIT_CODE. Restarting in ${RESTART_WAIT_SEC}s..."
    sleep "$RESTART_WAIT_SEC"
done

echo "[supervisor] Done. restarts=$RESTART_COUNT"
```

**Constraints:**
- Does not modify `main.py` or any production code
- Must be explicitly invoked (`run_live_supervised.sh`), not the default
- Inherits all safety env vars from calling shell
- Restart wait of 15s gives Kite session validity time to recover

## 9. What Could Still Fail (Residual Risk)

Even with all 10 MODs applied and env vars set:

1. **Kite API token expiry** (401/403 on reconnect): only resolved by fresh Zerodha session. Not fixable in code.
2. **Network outage > 60s**: ISP-level dropout; feed recovery requires Kite session validity.
3. **Option token resolution failure**: if `build_subscription_tokens` returns 0 tokens (instrument master not downloaded fresh), Phase2 stays empty regardless of feed health.
4. **SQLite write contention**: if tick insertion is slow (DB lock), `_latest_db_tick_epoch()` returns stale values → false `FEED_LTP_STALE`.
5. **NSE circuit halt / pre-open phase**: no option ticks during circuit-down periods; no code fix can help here.
6. **Kite OMS delays**: even if feed is healthy, order confirmations may arrive late; risk of manual approval flow blocking.
