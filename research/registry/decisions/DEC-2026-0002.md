# DEC-2026-0002 — Adopt Persistent MROS Program Branch and Promotion Policy

Status: ACTIVE
Decision date: 2026-08-08
Decision class: PROGRAM_EXECUTION_POLICY
Authority: User-directed operating model, implemented on `research/mros-program-v1`.

## Context

The MROS manual requires 120 controlled sprints with repository artifacts and evidence, but it does not require one pull request per sprint. The repository's generic CI runs on push and pull-request events, while additional review gates are concentrated on pull requests targeting `main`. Creating one PR per sprint would add process and CI cost without adding scientific authority.

## Decision

Use one persistent integration branch:

`research/mros-program-v1`

The 120 controlled sprints remain individually traceable through sprint-scoped commits, evidence manifests, and append-only ledgers. Pull requests are promotion boundaries rather than sprint containers.

### Commit policy

- Each controlled sprint receives at least one clearly identified sprint commit and a recorded sprint decision.
- Intermediate sprint commits may use `[skip ci]` when targeted/local verification evidence exists and the sprint is not a milestone acceptance checkpoint.
- `[skip ci]` never counts as QA evidence and never upgrades sprint authority.
- A skipped GitHub Actions run is recorded as skipped, not passed.
- Work-package acceptance requires all five associated sprint decisions plus the WP evidence seal required by the manual.

### CI policy

- Full repository CI is required at every milestone acceptance gate.
- A milestone cannot be `PASS` while required milestone CI is absent, pending, skipped, or red.
- Scientific acceptance additionally requires the manual's evidence, attack, reproducibility, and authority criteria; green CI is necessary but insufficient.

### PR policy

- No PR per sprint.
- No PR per work package by default.
- M1–M8 are developed on `research/mros-program-v1` and receive one reviewed promotion PR to `main` when M8 is accepted and promotion is authorized.
- M9 runtime/TradeBot integration is reviewed and promoted separately because it changes the research-to-runtime authority boundary.
- Existing bootstrap PRs #811 and #812 are superseded as execution vehicles; their repository commits/evidence remain reusable and traceable.

### Continuity policy

Every new agent/session must first read:

1. `research/program/MROS_PROGRAM_STATE.yaml`
2. `research/program/SPRINT_LEDGER.jsonl`
3. `research/program/WORK_PACKAGE_LEDGER.jsonl`
4. `research/program/MILESTONE_LEDGER.jsonl`
5. the active sprint evidence directory and applicable manual sections

Conversation memory may help navigation but cannot override these artifacts.

## Archive policy

Git history is the source of truth. Optional milestone ZIP snapshots may be created as sealed archival evidence, but ZIP files never replace Git lineage.

## Consequences

This policy reduces unnecessary CI/PR churn while preserving the manual's 120 sprint decisions and evidence chain. It also prevents skipped CI from being mistaken for verified CI.

## Rollback

A later recorded decision may change branch/CI/promotion mechanics after an impact review. Sprint identities, evidence, and historical decisions must remain preserved.

## Observed Facts

The user explicitly selected a persistent program branch, sprint commits, milestone CI checkpoints, repository state/ledgers, and two promotion boundaries: M1–M8 and M9.

## Inferences

PR count is an engineering workflow choice, not a scientific authority dimension. Evidence per sprint remains mandatory even when CI is not run for every intermediate commit.

## Hypotheses

None.

## Assumptions

GitHub's standard skip markers continue to suppress eligible push/pull-request workflows where configured by GitHub semantics; the program does not depend on skipped checks being reported as passing.

## Destroyers

A repository policy or branch-protection rule that makes this model impossible requires a new impact decision rather than silent workaround.

## Unknowns

The exact runtime cost of milestone CI may vary as workflows evolve.
